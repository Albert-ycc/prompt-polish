# 设计依据

## 要解决的问题

第一版改写原则是「原文缺什么补什么」。实际用下来，改写后的提示词常常抓不住重点。作者拿自己的历史草稿做了对照实验，发现问题不在核心句：核心句的准确度达到 1.87–1.95（满分 2）。真正把执行方带偏的是附加内容，主要有三类：

- **自加的约束**：把记忆里的通用规则（例如某种文档写入方式）转述成这次任务的硬约束，结果和草稿原意冲突；
- **待澄清项**：数量多、不排序，混进执行方自己就能查到的事，或者顺手引出草稿没提的新功能；
- **自定的默认值**：替用户写「我先按 X 走」，方向和用户真实意图相反。

## 现行改写原则

1. **只补关键缺口**：五个槽位（真实问题与背景、目标、产出物形态、范围与约束、完成标准）先判断「清楚 / 部分清楚 / 缺失」。只补缺了会让执行方做出明显不同结果的；其余合并成一行默认假设；不补原文没提到的具体约束。
2. **记忆分两类处理**：管这次产出边界的规则（不加没提的功能、不编造内容、以哪份原始材料为准、交付规格），落到这次任务上写成一句；管操作手法的通用规则不转述，因为执行方会自己加载。和草稿原话冲突时，以草稿为准。路径、文件名、项目名、系统名只能照抄见过的原文。
3. **待澄清只留用户才能回答的**：执行方能自己查到的，改成在正文里让它先去查；剩下的最多 3 条，按影响排序。不借待澄清引出新功能，不替用户写默认答案。
4. **开放探讨类的结尾**：先给判断和推荐做法，再列出最多 3 个关键问题，不让执行方空着手只提问。

## 验证方法

- **样本**：作者自己在 Claude Code 里敲过的会话开场草稿。每条附上同一会话里后续的追问和纠正，作为「用户真实意图」的参照。
- **改写**：每条草稿用各版本指令分别独立改写。旧指令独立跑两次，两次之间的差距作为噪声底线。
- **评审**：每条两个评审盲评，都能看到后续纠正，两人看到的版本顺序互逆。指标包括：名次、引发纠正次数（版本里恰好写出了用户后来纠正的内容）、提前避免纠正次数、编造条数、约束保留。
- **防过拟合**：调指令用的草稿和决选用的草稿分开。决选用 12 条从未用过的草稿，上线规则在开跑前写进脚本：领先旧指令超出噪声的版本里取名次最好的；差距在噪声内时，取引发纠正更少的。

## 决选结果（12 条从未用过的草稿）

| 版本 | 平均名次（1–5，越小越好） | 引发纠正 | 提前避免纠正 | 编造 |
|---|---:|---:|---:|---:|
| 旧指令（两次平均） | 3.46 | 0.15 | 0.69 | 0.08 |
| V1：只补关键缺口 + 交付规格可写、限制规则不转述 | 3.54 | 0.29 | 0.50 | 0.21 |
| V2：V1 的修订版，按调参样本收紧 | 2.38 | 0.25 | 0.46 | 0.08 |
| **V3：现行版本** | **2.17** | 0.25 | **0.75** | **0** |

- V3 对旧指令：12 条里赢 9 条、平 1 条、输 2 条。
- V3 对 V2 的差距在噪声以内；V3 编造为零，最终选它。
- V2 在调参样本上领先，但在另一批留出草稿上输给了 V1，有过拟合迹象。这也是最后要用全新草稿决选的原因。

## 已知问题

- 草稿本身没有给出边界时，偶尔会自己补出一句禁止句（例如「不要自己补流程」），反而挡住用户后来真正想做的事。
- 草稿提到要改需求文档时，PRD 有时只写成「有就一起改」，没有列为必须交付的产出。

## 局限

- 只评了改写出来的文本，没有让 Claude Code 照着执行一遍。
- 评审和改写用的是同一个基座模型。
- 样本只来自一位用户。不同领域、不同写作习惯下的效果没有验证过。
